# 九星気学の記録仕様

壁紙向け独自方式 `lucky-wallpaper-v1`。本命星は六白金星に固定し、月命星は使わない。特定流派への完全準拠や当選への効果を主張しない。判定・配置はアプリが確定し、外部AIはモチーフの表現、構図と画像を制作する。過去実績や分析結果は入力しない。

## 吉方位の固定判定

1. 盤内は後天定位の順で順飛する。五黄中宮なら北1・北東8・東3・南東4・南9・南西2・西7・北西6。日星の陰遁・陽遁は中宮の日ごとの変化であり、盤内の順を反転させない。
2. 二黒・八白・七赤・一白が回座する8方位を候補とし、その盤の五黄殺・暗剣殺・本命殺・本命的殺・破を除外する。破は日盤が日破、月盤が月破、年盤が歳破。十二支の対向を8方位へまとめ、斜めの破も方位全体を除外する。
3. 中宮に方位はない。五黄が中宮なら五黄殺・暗剣殺、六白が中宮なら本命殺・本命的殺の方位は追加しない。
4. 日盤＞月盤＞年盤の順に検査し、最初に候補が残った盤だけを採用する。3盤の共通部分は取らず、下位盤の比較はしない。
5. 複数候補は北→北東→東→南東→南→南西→西→北西の順に並べ、先頭を主方位とする。吉の強弱を表す順位ではない。
6. 全盤に候補がない場合だけ `none`（吉方位指定なし）。必要な盤の取得・計算に失敗したら `undetermined`（判定不能）として停止し、下位盤へ進まない。双方とも方位なし・中央配置・六白金星のモチーフで補完する。

候補分類は[徳風會](https://www.tokufu.net/9sei/kigaku.html)、破と中宮の扱いは[八雲院](https://yakumoin.info/about/houiban)の説明を参照した。組み合わせ全体は本アプリ用の採用仕様である。

## 暦と日付の境界

既存依存の `6tail/lunar-php`（composer.lockで固定）の節気と日干支を使用する。対象日は `LUCKY_TIMEZONE`（既定 `Asia/Ho_Chi_Minh`）の暦日。節気計算が返すUTC+08:00の時刻を現地へ変換してから日付を取る。日本の節入り日を流用しない。

- 年盤は立春が属する現地日の0時から切り替える。中宮は西暦年に対応した9年周期、年支も立春基準とする。
- 月盤は十二節入りが属する現地日の0時から切り替える。寅月の中宮を子午卯酉年は八白、辰戌丑未年は五黄、寅申巳亥年は二黒とし、翌月ごとに1つ減らす。旧暦の朔・閏月は使わない。
- 日界は現地0時。23時の子刻で翌日扱いにしない。現地の夏至・冬至の日干支から至近の甲子（六十干支の番号0～29なら直前、30～59なら直後）を求める。通常は夏の甲子を九紫の陰遁、冬の甲子を一白の陽遁の起点とする。
- 隣接する甲子起点が240日離れる場合は、最後の60日を閏とし、前半30日は従来の遁を継続、後半30日から反転する。夏は三碧、冬は七赤で反転し、その星が2日続く。これは[こよみのページの明示された計算法](https://koyomi8.com/sub/9sei.html)を採用したもので、流派間の普遍的な正解を意味しない。

一日一枚のため節入り時刻の前後で一枚を分割せず、現地の節入り日全体へ新盤を適用する。対応範囲は1901～2099年。範囲外や不正な暦は判定不能にし、AIで補わない。テストは立春・節入り・年またぎ・通常転遁・夏冬の置閏・ベトナムと日本で日付が異なる節気を固定期待値で検証する。

## 独立した期待値による検証

変更前はアプリ内の暦計算を行わず、AIが流派・暦・方位を判断していた。既存の計算処理を改修したものではない。今回、既存依存のlunar-phpから節気・日干支を取得する計算と、上記の年・月・日盤および除外・選択処理をアプリに新設した。

テストの期待値は次の公開資料から固定している。`KigakuCalendar` の出力をそのまま暦の正解として生成していない。HTTP保存テストの `currentPayload` は入力と保存の往復検証用であり、暦の正しさは別の固定値テストで検証する。

| 検証 | 独立した期待値・出典 |
| --- | --- |
| 立春・ICT日付 | [国立天文台2017暦要項](https://eco.mtk.nao.ac.jp/koyomi/yoko/2017/rekiyou172.html)の立春2月4日00:34 JST → 2月3日22:34 ICT。ICTでは2月3日の0時から年・月盤を切り替え、日本設定の2月4日とは区別する |
| 節入り・ICT日付 | [国立天文台2026暦要項](https://eco.mtk.nao.ac.jp/koyomi/yoko/2026/rekiyou262.html)の啓蟄3月5日22:59 JST → 20:59 ICT、芒種6月6日00:48 JST → 6月5日22:48 ICT。後者はICTの6月5日から月盤を五黄→四緑へ切り替える |
| 通常転遁 | [八雲院2026カレンダー](https://yakumoin.info/about/kyusei_calendar)の6月18日九紫→19日九紫・陰遁→20日八白、12月15日一白→16日一白・陽遁→17日二黒 |
| 夏の置閏 | [Magic Wands 2020年6月](https://www.magicwands.jp/calculator/calendar/?month=6&year=2020)の19日三碧→20日三碧・陰遁→21日二黒 |
| 冬の置閏 | [Magic Wands 2031年12月](https://www.magicwands.jp/calculator/calendar/?month=12&year=2031)の19日七赤→20日七赤・陽遁→21日八白 |
| 日付入力の境界 | UTCサーバーで6月18日16:59:59 UTC＝ICT23:59:59の翌日初期値は6月19日、17:00:00 UTC＝ICT翌日0時では6月20日になることをHTTPテストで確認 |

節気時刻には公開資料の分単位への丸めとライブラリの天体暦差を考慮して61秒未満の許容差を置くが、現地日付は完全一致を要求する。九星暦の公開例は日本の日付をそのまま全日に流用するのではなく、上記転遁例の照合に使う。日付が異なる立春・芒種は天文時刻をICTへ換算して別途検証する。

## 方位から画像への変換

画面左上を原点とし、上＝北、右＝東の象徴的な配置を使う。南が上の九星盤の表示座標やスマホを向ける地理的方位とは別である。

| 主方位 | 左から | 上から |
| --- | --- | --- |
| 北 | 50% | 40% |
| 北東 | 70% | 40% |
| 東 | 70% | 55% |
| 南東 | 70% | 70% |
| 南 | 50% | 70% |
| 南西 | 30% | 70% |
| 西 | 30% | 55% |
| 北西 | 30% | 40% |
| 指定なし・判定不能 | 50% | 55% |

上部30%は時計用余白。主役は1つ、自然光、上昇感を保ち、南でも下降表現にしない。縦9:16、推奨1440×2560。文字・数字・ロゴ・署名・透かしなし。銀白と自然素材を尊重し、露骨な財宝・金貨・人工的な金色発光を避ける。

モチーフと質感は `KigakuPolicy::MOTIFS` を正本とし、採用方位の回座星で選ぶ。補完時は六白。表の範囲内で画像表現に変化をつける。

| 九星 | モチーフ | 質感 |
| --- | --- | --- |
| 一白 | 水滴・清流・白い水鳥 | 透明な水、自然の反射 |
| 二黒 | 野の草花・田園の草穂 | 土、生成りの繊維 |
| 三碧 | 若芽・若木 | 緑、木の繊維 |
| 四緑 | 柳葉・風になびく草 | しなやかな葉 |
| 五黄 | 自然石・大地の稜線 | 自然の土と石 |
| 六白 | 白い鳥・銀白の自然石 | 銀白、控えめな自然の光沢 |
| 七赤 | 白い花・水辺の鳥 | 花弁、淡い銀白の反射 |
| 八白 | 山の稜線・岩に根づく植物 | 自然岩、積層した石 |
| 九紫 | 朝日に照らされた花・明るい羽の鳥 | 自然光を受けた花弁や羽、控えめな赤紫 |

## JSON・保存・互換性

ルート必須項目はtitle、art_style、conclusion、overview、composition、color_wu_xing、symbolism、kigaku。titleとart_styleは255文字以内。conclusionは「構図名 × 画風」。旧feng_shui・composition_zoneは新規JSONで受け付けない。

入力の `fixed_kigaku` をそのまま `kigaku` へコピーし、`motifs` を追記する。アプリは下表の固定値を再計算して比較し、食い違う場合は画像保存前に拒否する。構図の文章と実画像の一致は手動受入で確認する。

| 項目 | 内容 |
| --- | --- |
| policy_version | lucky-wallpaper-v1 |
| target_date / personal_star / timezone | 対象日 / 六白金星 / 設定タイムゾーン |
| status | auspicious / none / undetermined |
| selected_board | day / month / year / null |
| candidate_directions | 採用盤の候補を固定順に並べた配列 |
| primary_direction | 候補の先頭、またはnull |
| direction_star | 採用方位の回座星の番号1～9、またはnull |
| subject_position | x_percent・y_percentによる主役中心 |
| method / reason | 固定方式・暦の基準 / 検査した盤と除外・採用理由 |
| fallback_reason | 補完時の理由、吉方位ありならnull |
| motifs | 固定表の名称motifと、その象意の説明meaning |

新規プロンプトは出典一覧・出典URL・referencesを出力しない。references付きのJSONも他の現行条件を満たせば受理する。参照資料はHTTP(S)またはnullのurlを検証し、過去の保存済み参照資料も保持する。

既存 `composition_proposals.calendar_context` に `policy_version` と `kigaku` を保存する。新しいDBマイグレーション、方式の開始日・適用日フィールド、日付による旧新方式の切替は追加しない。通常の対象日・作成日時は保持する。過去の構図・画像・実績は再計算・再分類・一括書換えしない。旧版の未登録JSONは現行プロンプトで作り直す。

新規作成と再作成は同じ固定方式を使用する。画像だけの再生成は保存済み構図・判定・位置を使用し、現在の暦で再判定しない。旧データには新方式の配置を推測して追加しない。

JSONと画像は同時に検証・保存し、失敗時はDBと新規ファイルを残さない。新規analysis_hashはnull。同日再提案やプロンプト変更で古くなった入力は再取得を求める。

## 集計

同じ壁紙に属するapprovedのchosen_proposalだけを主方位別に集計する。候補方位へ重複計上しない。none、undetermined、判定情報のないlegacyは別グループ。本文のみのNotion復元レコードから方位を推測しない。旧版と新版は保存済みprimary_directionで同じ集計へ参加できる。

賞金未登録と0を区別する。1日平均は賞金合計÷実績登録件数、1口あたり賞金は口数既知の賞金合計÷その購入口数合計。口数不明の賞金は後者の分子へ含めない。
